## OPEN FINDING — `dataAgeMs` latency metric is not measuring staleness

Diagnosed, **fix proposed but NOT applied** (owner to review; applying it
means restarting the live shadow, which was explicitly deferred).

- **Root cause:** `main.ts:147` computes
  `dataAgeMs = Date.now() − max(snapshot.fetchedAtMs)`, but every source
  sets `fetchedAtMs` to *its own receipt time* — polling sets it to
  `Date.now()` right after the RPC await (`polling.ts:101/108/131`,
  `orcaOrcaPolling.ts:103`) and then calls `onPair` synchronously; Geyser
  uses `receivedAtMs` (`geyser.ts:93`). So the metric measures the
  sub-millisecond receipt→detect handoff (floors to 0: p50=p95=0, 96.2%
  exactly 0), NOT the age of the data relative to the chain
  (block-landing → our read). No chain-relative timestamp (block time of
  the data's slot) is ever attached.
- **Scope:** affects polling AND Geyser identically → the metric cannot
  differentiate them, defeating the whole point of the Phase-2
  Geyser-vs-polling latency comparison. `fetchedAtMs` (snapshot) has a
  single consumer (this calc), so a fix is well-contained;
  `getBlockTime`/`getSlot` are not used anywhere yet.
- **Status:** run latency numbers are not trustworthy and must not be
  cited (noted in the phase-2 doc). Proposed fix awaiting owner decision.
